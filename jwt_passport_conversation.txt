JWT, PASSPORT & AUTHORIZATION - FULL CONVERSATION NOTES
================================================================


----------------------------------------------------------------
Q1: Explain JWT, Passport, LocalStrategy, JwtStrategy,
    Why two strategies, and the role of JWT_SECRET
----------------------------------------------------------------

WHAT IS JWT?
------------
A JSON Web Token is a compact, self-contained string used to
securely transmit information between parties. It has three
base64-encoded parts separated by dots:

  HEADER . PAYLOAD . SIGNATURE

- Header:    algorithm used (e.g. HS256)
- Payload:   claims like { userId: 123, email: "a@b.com" }
- Signature: HMAC(header + "." + payload, JWT_SECRET)
             proves the token wasn't tampered with

JWTs are stateless — the server doesn't store them.
It just verifies the signature on each request.


WHAT IS PASSPORT?
-----------------
Passport is an authentication middleware for Express. Its job is to:

1. Intercept a request
2. Extract credentials from it (body, header, cookie, etc.)
3. Validate those credentials using a strategy
4. Attach the authenticated user to req.user (or reject)

Passport itself is just a runner — all real logic lives in strategies.


THE TWO STRATEGIES & WHY YOU NEED BOTH
---------------------------------------
Login and subsequent requests are fundamentally different problems:

  PROBLEM 1: "Who are you?"        → LocalStrategy
  PROBLEM 2: "Are you still you?"  → JwtStrategy


LocalStrategy — The Login Gate
  Used ONCE, at the /login endpoint. It:
  1. Extracts username and password from req.body
  2. Looks the user up in the database
  3. Compares the password hash (via bcrypt.compare)
  4. If valid → issues a JWT

  passport.use(new LocalStrategy(async (username, password, done) => {
    const user = await User.findOne({ username });
    if (!user) return done(null, false);
    const valid = await bcrypt.compare(password, user.passwordHash);
    return valid ? done(null, user) : done(null, false);
  }));

  After login, LocalStrategy's job is done — it never runs again.


JwtStrategy — The Session Replacement
  Used on EVERY protected route. It:
  1. Extracts the token from Authorization: Bearer <token> header
  2. Verifies the signature using JWT_SECRET
  3. Decodes the payload (e.g. { userId: 123 })
  4. Attaches the result to req.user

  passport.use(new JwtStrategy({
    jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
    secretOrKey: process.env.JWT_SECRET
  }, async (payload, done) => {
    const user = await User.findById(payload.userId);
    return user ? done(null, user) : done(null, false);
  }));


THE ROLE OF JWT_SECRET
-----------------------
JWT_SECRET is the signing key — the single secret that makes
the whole system trustworthy.

  Sign:   HMAC(header + payload, JWT_SECRET) → produces signature
  Verify: HMAC(header + payload, JWT_SECRET) → must match token signature

- At login:        server uses it to SIGN the token
- On each request: JwtStrategy uses it to VERIFY the token
- If payload is tampered with → signature won't match → rejected
- If JWT_SECRET leaks → anyone can mint valid tokens

  JWT_SECRET=some_long_random_string   # never hardcode, never commit


THE FULL FLOW
-------------
  Client                         Server
    │                              │
    ├── POST /login ─────────────► │  LocalStrategy runs
    │   { username, password }     │  → verifies password against DB
    │                              │  → signs JWT with JWT_SECRET
    │◄── { token: "eyJ..." } ─────│
    │                              │
    ├── GET /profile ────────────► │  JwtStrategy runs
    │   Authorization: Bearer eyJ  │  → verifies signature with JWT_SECRET
    │                              │  → decodes payload, loads user
    │◄── { name: "Alice", ... } ──│

Q2: Is LocalStrategy for authentication and JwtStrategy
    for authorization?
----------------------------------------------------------------

NOT QUITE — both are authentication. Here are the real definitions:

  Authentication  →  "Who are you?" — prove your identity
  Authorization   →  "What are you allowed to do?" — check permissions

LocalStrategy  →  Authentication (identity establishment) — "Here's my password"
JwtStrategy    →  Authentication (identity verification)  — "Here's my token"
Role/permission→  Authorization — "Can this user do this action?"

Authorization happens AFTER JwtStrategy, using req.user:

  app.delete('/post/:id',
    passport.authenticate('jwt', { session: false }),  // Authentication
    requireRole('admin'),                               // Authorization
    deletePost
  );

- 401 Unauthorized → bad/missing token (authentication failed)
- 403 Forbidden    → valid token but insufficient permissions (authorization failed)

Q3: How do you implement authorization?
----------------------------------------------------------------

1. STORE ROLE ON USER MODEL
   {
     _id: "123",
     email: "alice@example.com",
     role: "admin",
     permissions: ["read:posts", "delete:posts"]
   }

2. EMBED ROLE IN JWT AT LOGIN
   const token = jwt.sign(
     { userId: user._id, role: user.role },
     process.env.JWT_SECRET,
     { expiresIn: '1h' }
   );

3. requireRole MIDDLEWARE
   function requireRole(...allowedRoles) {
     return (req, res, next) => {
       if (!allowedRoles.includes(req.user?.role))
         return res.status(403).json({ error: 'Forbidden' });
       next();
     };
   }

   app.get('/posts',        authenticate,                       getPosts);
   app.post('/posts',       authenticate, requireRole('editor'), createPost);
   app.delete('/posts/:id', authenticate, requireRole('admin'),  deletePost);

4. GRANULAR PERMISSIONS
   function requirePermission(permission) {
     return (req, res, next) => {
       if (!req.user.permissions?.includes(permission))
         return res.status(403).json({ error: `Missing: ${permission}` });
       next();
     };
   }

5. RESOURCE OWNERSHIP
   function requireOwnership(Model) {
     return async (req, res, next) => {
       const resource = await Model.findById(req.params.id);
       const isOwner = resource.authorId.toString() === req.user.userId;
       const isAdmin = req.user.role === 'admin';
       if (!isOwner && !isAdmin)
         return res.status(403).json({ error: 'Forbidden' });
       req.resource = resource;
       next();
     };
   }

FULL CHAIN:
  Request
    → JwtStrategy       (who are you?)           401 if bad token
    → requireRole       (right role?)             403 if wrong role
    → requirePermission (right permission?)       403 if missing
    → requireOwnership  (your resource?)          403 if not yours
    → route handler     (do the actual work)


----------------------------------------------------------------
Q4: Should authorization check the role from DB or JWT?
----------------------------------------------------------------

You have a choice:

OPTION A — Trust the JWT Payload (no DB hit)
  - Role baked into token at login
  - Authorization reads req.user.role directly
  - Pro: Fast — zero DB queries
  - Con: Stale — role changes don't take effect until token expires

OPTION B — Always Check the DB
  - Query User.findById on every protected request
  - Pro: Always accurate
  - Con: Extra DB query per request

REAL WORLD — Hybrid approach:
  - JWT carries userId + role (handles 99% of requests fast)
  - DB queried only for sensitive actions or after known role changes
  - Short token expiry (15m) limits the stale-role window

  jwt.sign(payload, JWT_SECRET, { expiresIn: '15m' })

THE BOTTOM LINE:
  Passport  →  gives you req.user (authentication only)
  JWT       →  carries the data (userId, role)
  Your code →  checks that data against rules (authorization)

  No built-in solution exists — you build it.
  Authorization logic is always YOUR responsibility.
